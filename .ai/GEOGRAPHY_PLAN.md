===== PLAN: Geography =====
Models (new app geography, based on BaseModel): Country (ISO2 code, name_uz/ru/en, currency, is_active, sort_order), Region (FK Country, names, is_active, sort_order), City (FK Region, names, is_active, sort_order). Use PROTECT on deletes: anything in use can be hidden (is_active=false) but not deleted.
Property gets nullable country_ref, region_ref, city_ref FKs. The old text fields country/state/city STAY and are filled automatically from the English names whenever the FKs are set, so booking, accounts and other old code keep working. Removing the text fields is a separate, later cleanup: do NOT do it now.
Initial data (idempotent, a data migration or seed command): Uzbekistan in full: Andijan, Bukhara, Fergana, Jizzakh, Khorezm, Namangan, Navoi, Kashkadarya, Samarkand, Sirdarya, Surkhandarya, Tashkent region, Republic of Karakalpakstan, Tashkent city (14 first-level regions), each with its regional centre and well-known tourist cities (for example Khiva, Shahrisabz, Kokand, Margilan, Termez, Nukus, Urgench). Kazakhstan and Turkey with the regions and cities used by the demo data plus a few major ones. Names in uz/ru/en, for example Toshkent / Ташкент / Tashkent, Samarqand / Самарканд / Samarkand, Buxoro / Бухара / Bukhara, Farg'ona / Фергана / Fergana, Xorazm / Хорезм / Khorezm, Qoraqalpog'iston Respublikasi / Республика Каракалпакстан / Republic of Karakalpakstan. Mark in a comment that the uz/ru names need a native-speaker review.
Mapping of existing properties: match the text fields, trimmed and case-insensitive, against all three name columns plus a few aliases (Uzbekistan, O'zbekiston, Ozbekiston, Узбекистан, UZ and similar). Unmatched values stay NULL and are printed in a dry-run style report with counts. Forward and reverse migration tests.
Public API: GET /geography/countries/ (active only, with hotel counts via one annotated query), GET /geography/countries/{code}/regions/, GET /geography/regions/{id}/cities/. Return all three names and let the frontend choose the language; until i18n exists, the frontend shows the English name.
Admin API: super-admin CRUD under /admin-panel/geography/ (create, edit, hide/show, reorder, search). Extend the access-matrix tests.
Property writes: partner and admin serializers accept country_ref, region_ref and city_ref ids. Validate that the region belongs to the country, the city to the region, and all are active. Creating a property requires all three.
Search: location search and suggestions match names in all three languages through the FKs, and still fall back to the old text fields for unmapped rows.
Status: group by the FK. URLs move from names to ISO code (country) and ids (region). This is a breaking API change: update .ai/API_CONTRACT.md and change the frontend adapters in the next commit. Properties with NULL refs are grouped as "Unspecified", as before.
Frontend: (1) super-admin "Geography" screen: tree of country > region > city, add/edit, hide/show, search, reorder. (2) Partner wizard: cascading dropdowns country > region > city instead of free text. Admin moderation: dropdowns instead of the free region input, and the admin may fix country and city too. (3) DestinationsPage and the featured destinations on HomePage read from the public endpoint instead of hardcoded lists. (4) Status adapters and pages use the new keys.
Phone country selector: a SEPARATE static list of at least 40 countries (Central Asia, CIS, Turkey, Gulf, Europe, US/Canada) with dial code, name in uz/ru/en, searchable. Flags are SVG files or a small MIT-licensed SVG flag set bundled locally (no CDN, because of the CSP), never emoji. The selector replaces the flag span in PhoneInput; UZ stays the default and keeps its formatting and 9-digit limit; other countries allow up to 15 digits in total (E.164 maximum) and the backend keeps validating. Used in Login, Register, Profile and Booking. This list is independent of the hotel countries.
Steps
G1 backend: geography app, models, schema migration, initial data.
G2 backend: Property FKs, mapping migration with report, text fields kept in sync, forward/reverse tests.
G3 backend: public and admin geography endpoints with access-matrix tests.
G4 backend: property serializers with FK validation, three-language search and suggestions, status grouping by FK, API contract update.
G5 frontend: Geography admin screen.
G6 frontend: cascading dropdowns, admin moderation dropdowns, destinations and home from the public endpoint, status adapters on the new keys.
G7 frontend: phone country selector with SVG flags.
G8 E2E: an owner creates a hotel picking country > region > city; the admin adds a new country, region and city in the Geography screen and they appear in the wizard and the public endpoint; searching "Ташкент", "Toshkent" and "Tashkent" finds the same hotel; the phone selector switches country and formats the number; Status counts that hotel under one country.

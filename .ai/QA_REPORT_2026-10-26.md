# QA run, 2026-10-26: the site used as a guest, an owner and an admin

Nothing was fixed in this run; this file is the list, in order of importance. Each finding says where, how to repeat it, what was expected, what happened, and a suggested fix.

## How it was done

- The production build of the frontend (`npm run build` + `vite preview`) against the Django backend and the demo database (Chromium only, 1440 and 390 px, en/ru/uz).
- About 400 automated API checks (sign-up, login, permissions and other people's ids, booking rules, input fuzzing, search, admin lists, owner forms, photo upload, chat, throttling).
- A sweep of every page for the four roles in three languages and two sizes (console errors, failed requests, sideways scrolling, raw translation keys, headings, labels).
- The project's own browser suite (`npx playwright test`, 28 tests): 25 passed, 3 failed (see F6).
- The built site served with the exact Content-Security-Policy of `deploy/nginx.conf.example` (see F1).
- Test accounts, bookings and hotels made by the run were deleted afterwards; the demo ads (ids 1 to 6) were moved to end on 2026-11-15 because they had ended on 2026-10-25.

## Findings, most important first

### F1. HIGH: the nginx example blocks the map tiles, so every map would be empty in production
- Where: `deploy/nginx.conf.example` line 42, `img-src 'self' data: blob:`; the map loads `https://tile.openstreetmap.org/{z}/{x}/{y}.png` (`frontend/src/components/mapTiles.ts`).
- Repeat: serve `frontend/dist` with the header of that file and open `/property/3`.
- Expected: map tiles load. Got: every tile request fails with `Refused to load the image 'https://tile.openstreetmap.org/...' because it violates ... img-src`. No other page showed any other CSP violation (guest, customer, owner and admin pages were visited).
- Fix: add the tile host to `img-src` (or serve tiles from the site's own domain); add a test that compares the nginx example with the hosts the frontend loads. Check the OpenStreetMap tile usage policy for production traffic.

### F2. HIGH: e-mail addresses are case sensitive (duplicate accounts and failed sign-in)
- Repeat: register `GUEST@tickbron.demo` while `guest@tickbron.demo` exists: 201, a second account (id 94 in the run). Sign in with `Guest@Tickbron.Demo` and the right password: 401.
- Expected: one account per address whatever the capitals; sign-in works with any capitals.
- Impact: phone keyboards capitalise the first letter, so real guests may be unable to sign in; two accounts can exist for one mailbox.
- Fix: store and compare the address in lower case at register, login and password reset, add a case-insensitive unique constraint (check existing data for duplicates first, with a migration).

### F3. MEDIUM: an approved hotel with no room, no rate and no photo is public
- Repeat: an owner creates a hotel; the admin approves it (`POST /admin-panel/properties/{id}/approve/` returns 200). It appears in guest search and its page shows 0 rooms and 0 photos.
- Expected: approval is refused (or the hotel stays hidden) until there is at least one room with an active rate and a photo.
- Fix: check in the approve action; show the missing parts to the admin.

### F4. MEDIUM: the children list of a booking is not validated
- Repeat: `POST /api/v1/bookings/` with `children: [5, 5, ... 100 times]`: 201 and all 100 are saved. One guest with three children, and two guests with four children in a room for two, are also accepted.
- Expected: a sensible limit on the number of children, and a decided rule on whether children count towards the room's capacity.
- Fix: limit the count in the booking serializer and say in the contract whether children use capacity.

### F5. MEDIUM: owner forms miss basic sanity rules
All accepted with 201 (the API should answer 400):
- rate plan with `min_nights` 10 and `max_nights` 2 (the plan can never be booked), and `max_nights` 99999;
- room type with `max_occupancy` 2 below `base_occupancy` 4, `total_rooms` 0 and 100000;
- hotel with `base_price` 0 and 999 bathrooms;
- date inventory in the past, and `available_rooms` 9999 above the room's total.
Fix: add the checks in the partner serializers (same place as the existing price and date checks), with tests.

### F6. MEDIUM: the browser (E2E) suite is not run by CI and has gone stale
- S7 (owner sees only own numbers) fails: "On TICKBRON since" moved to the Reports tab in Owner Status v2; the test still expects it on the Overview tab. A test left behind by our own change.
- J1 (promotion banner) fails when the demo ads have ended (they ended 2026-10-25); with fresh dates it passes.
- E1 (owner panel) expects exactly 3 hotels; it failed only because this run had left test hotels (passes after the cleanup).
- The three crawl tests take 6 to 11 minutes each.
- Fix: update S7; make the demo seed dates relative to the day the suite runs; run the suite nightly in CI on a fresh seed.

### F7. LOW to MEDIUM: owners see technical English messages
- Repeat: add a room with a slug that exists in the hotel: the alert says "The fields property, slug must make a unique set." (English, jargon). The form also asks the owner to type a "Slug" (untranslated technical word) by hand for rooms and rates.
- On the API, the `message` of validation errors from the partner and admin amenity endpoints is a Python dump (`{'category': [ErrorDetail(string='This field is required.', code='required')]}`); the `details` field is correct.
- Fix: generate the slug from the name, translate the refusal, and build `message` from the readable text.

### F8. LOW: no limit on the number of hotel photos
Uploaded 44 photos to one hotel without a refusal (rooms allow 20, ads 10). Fix: choose and enforce a limit.

### F9. LOW: empty names are accepted
Sign-up with an empty `full_name` gives 201 with the address as the name; a booking with an empty `guest_full_name` gives 201 (the account name is used). The forms ask for names, only the API is lax.

### F10. LOW: a business rule answers with HTTP 429
"Too many upcoming bookings" (limit 2) returns 429, the same status as throttling. Clients and monitoring may mistake it for a rate limit. Consider 409 or 422 (the code `too_many_upcoming_bookings` is already there).

### F11. LOW: the browser's own form messages are not in the site language
Sign-up and login use native validation ("Please fill out this field." in the browser's language, not uz/ru/en of the site).

### F12. LOW: status endpoints ignore bad dates silently
`/admin-panel/status/overview/?date_from=x` and a reversed range answer 200 with the default period instead of 400.

### F13. LOW: wording and headings of some empty and error screens
- `/booking` opened without a selected room: "Back to Property" has no property to go back to; no `h1`.
- An owner's "My Bookings" page speaks to guests ("book your first stay"); no `h1`.
- Property not found: "Property Not Found" and "Property not found" are repeated; no `h1`.

### F14. INFO for operations
- Promotion status (`scheduled`, `active`, `ended`) changes in the nightly Celery beat job at 00:10; until then an ended ad still shows as `active` in the admin list (the banner itself is date based and correct). Same for exchange rates (the demo database shows a rate dated 2026-10-19 with `stale: true`). Production needs Celery worker and beat (already in the launch list).
- The API schema and docs are open in DEBUG mode; the checklist asks to block them at the proxy in production.

## Checked and fine

- Sign-in and sign-up: invalid and hostile input (SQL, script, null byte, 5 MB body, broken JSON) never gives 500; the same answer for a wrong password and an unknown address; the same answer for a known and unknown address on password reset; the account cannot make itself staff.
- Permissions: guests are kept out of owner and admin areas, owners out of admin areas, nobody can read or cancel another guest's booking, an owner cannot read, edit or delete another owner's hotel, room or photos.
- Money: the quote, the created booking and the screen show the same total; client-sent price, status and guest fields are ignored.
- Booking rules: overlap refused, limit of 2 upcoming bookings, a past arrival time refused, six simultaneous requests for the last room give exactly one booking, six identical clicks give one booking, double cancel refused.
- Search and public endpoints: 34 hostile parameter sets and 18 public URLs, no 500, all fast (under 0.5 s).
- Admin lists: every list answers with bad paging, search and ordering, no secrets or password hashes in answers.
- Uploads: text, empty, SVG with script, HTML, PHP-in-JPEG, PDF, exe and 11 MB files refused; a 49-megapixel image refused; the stored file name is random.
- Throttling: login blocks at the 11th wrong attempt (the right password is also refused during the block), sign-up and password reset at the 6th.
- Chat: sizes, empty text, forged `from_staff`, unread counts, other users cannot see a thread.
- Translations: no key missing in ru or uz; only 26 entries equal the English text and they are names, formats or the word "Slug". No hard-coded English text found in the components.
- Phone sizes: no sideways scrolling on any page of the sweep.

## Not covered
